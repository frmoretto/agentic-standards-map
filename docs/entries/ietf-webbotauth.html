IETF Web Bot Auth (webbotauth WG)

IETFvenuecore entry

Verified 2026-10-26. Status as of 2026-10-26. All entries.

Seams: S3

Status

Active Working Group (WG), listed for coordination by the draft W3C Agentic Web charter; the first WG draft, draft-ietf-webbotauth-httpsig-protocol-00, was adopted on 2026-09-01, and a two-hour session was requested for IETF 127 on 2026-09-15. Implementation reports and proposed edits to the draft were on the list between 2026-10-04 and 2026-10-13. On 2026-10-13 the datatracker listed draft-ietf-webbotauth-httpsig-protocol-00 (2026-09-01) as the only WG draft, and it still did on 2026-10-26 (API: one draft in the group, revision 00). In the thread on updates to the crawler best practices draft a participant posted a revised text proposal on 2026-10-12 for a distinct Signature-Agent URL, key and key directory per crawler purpose, with pull requests in the WG draft repository and as PR #23 of garyillyes/cbcp. On 2026-10-22 PR #23 ("Identify crawler purposes with distinct Signature-Agent URLs") was merged and issue #3 of the same repository was closed as a duplicate; PR #140 of the WG draft repository, "Separate crawler and agent signing identities", which calls itself a companion to cbcp PR #23, was merged the same day; and revision -01 of the individual draft draft-illyes-webbotauth-cbcp was published (no stream, "I-D Exists", expires 2027-04-25). Its section 2.2 recommends "a distinct Signature-Agent URL, and therefore a distinct key directory, for each crawler purpose"; the text of -01 contains neither "429" nor "Retry-After", and PR #22 of garyillyes/cbcp, on those signals, was open on 2026-10-23. Also on 2026-10-22 the individual draft draft-kelley-webbotauth-sail-00, "SAIL: Source Address Identity List", was published: "a metadata format served at a well-known URI in which the operator of automated HTTP clients publishes the IP prefixes its services send from". On 2026-10-23 the datatracker recorded the webbotauth session at IETF 127 as "Waiting for Scheduling"; on 2026-10-26 the agenda of the meeting schedules it on Tuesday 2026-11-17, 16:30 to 18:30 San Francisco time (America/Los_Angeles, UTC-8), room Continental 4.

Relevance

The WG standardises cryptographic authentication of automated clients (HTTP message signatures, key directories), which a seller or its content delivery network (CDN) can use to tell which agent is calling. The chairs wrote on 2026-09-01 "Based on the feedback on the mailing list, the WG decided to adopt this draft as a WG document." Participants wrote of merchant-side verifiers: "We operate a production merchant-side verifier for automated commerce traffic (Web Bot Auth, Visa TAP, Google AP2)" (2026-08-03) and "We have implemented and use WBA for bot auth at Shopify in production, and we landed WBA interop for UCP" (2026-08-19).

On 2026-10-04 a participant from Auth Your Agent reported an implementation in which a user withdraws an agent by serving its key directory with no keys, cut max-age from 3600 to 300 because "an hour is a long time when the agent has just bought something the user disputes", and asked that verifiers respecting Cache-Control become a normative SHOULD in section 5.5.2 (the draft's appendix C.4 says they "should respect Cache-Control"); Thibault Meunier replied on 2026-10-07 "It seems that the simpler solution would be to prevent the agent from making request in the first place." On 2026-10-08 a participant from Akamai, writing as a verifier, supported moving the C.4 guidance into section 5.5.2 as normative text and proposed "Verifiers SHOULD NOT treat a cached directory as fresh beyond its freshness lifetime as defined in Section 4.2 of [HTTP-CACHE], except as permitted by Section", adding that "short signature expires values (Section 6.3) act faster than any directory TTL". The same day a participant, who publishes per-agent keys as a DNSSEC-signed record set and deactivates an agent by removing its key, wrote that "Section 5.5.2 bounds the wrong thing": where the key set reaches a verifier as a signed artifact (section 5.5.3), "the bound is the Appendix B signature's expires rather than any cache lifetime", and he measured on his apex "TTL 300 seconds against a signature window of 14 days and 1 hour". He proposed a sentence for 5.5.2 on the signature's expires and noted that section 6.3 (removal as the only remedy) and appendix C.12 (manual key rotation as the only revocation mechanism, listed as an anti-pattern) read as a contradiction when taken together. that participant answered on 2026-10-08 that his directories sent max-age=300 while the Appendix B proof on each was valid for 7 days, that he had cut the proof to one hour with a re-signature every 15 minutes, and that he supported the text of the participant who publishes per-agent keys.

On 2026-10-09 the same participant wrote that "The revocation thread got me reading the rest of the draft" and proposed for Appendix C.1 to replace "or the key is unknown" with "or the resolved directory does not provide the key", because a verifier could read an unknown key as "the key isn't on my list of bots" and so put a new agent that signs correctly in the same "unverified" outcome as a failed fetch; he also asked whether the draft should say anything about an intermediary that signs all its users' requests with one operator key, where removal under section 6.3 withdraws every user at once.

On 2026-10-07 a participant asked whether two bots with different purposes from one operator should have distinct Signature-Agent values and proposed a statement "So it's clear different Signature-Agents need to be used for different purposes / use cases."; he wrote that section 4.1 makes the Signature-Agent URL the identifier.

A participant from hCaptcha answered that it is similar to an open proposal, pull request #23 of garyillyes/cbcp, and that some crawl operators already do it, and wrote "I would support this proposal." On 2026-10-08 the same participant from Akamai supported a Signature-Agent per crawler purpose on the cbcp thread, citing that section 6.5 of the protocol draft "already says implementations SHOULD NOT reuse a signing key for different purposes and should use distinct keys and directories" and that "A signature that spans several purposes verifies fine but cannot carry that policy."; he asked that the 6.5 example be broadened to "an operator that runs both crawlers and user-directed agents". The crawler best practices draft (draft-illyes-webbotauth-cbcp, individual) was changed on 2026-10-05 (commit cc9942d of garyillyes/cbcp) and announced on the list the same day: a note that the practices "are intended for crawlers" and are "not necessarily appropriate for all automated clients", particularly "user-directed AI agents"; the requirement levels of the recommended practices changed from MUST to SHOULD; the proposal for a central crawler registry removed; and a Security Considerations section written, which says the opt-outs "are voluntary and do not constitute access control or content security measures" and that the User-Agent "is unauthenticated and trivially spoofed". Pull request #22 of garyillyes/cbcp (the author of this map, opened 2026-09-26, 429 and Retry-After in the back-out logic and a 429 on robots.txt read as unreachable) and #23 (opened 2026-10-06 by a participant, distinct subdomains for different crawl types) were both open on 2026-10-09; the only comment on #22 is of 2026-10-06 and reads "Common Crawl has always treated 429 as unreachable.", and in the announcement Gary Illyes wrote "I'm reviewing the pending PR to explicitly cover HTTP 429 and Retry-After". On 2026-10-05 a participant reported that his REDbot implementation emits signatures only when challenged ("the decision to only emit WBA when challenged") and that his agent-census log analyser sees "a reasonable number of bots emitting WBA by default"; he wrote that this is "an interoperability issue" worth highlighting in the document.

Thibault Meunier proposed on 2026-10-07 for section 5.3 "An Origin that expects a signature SHOULD request one from clients that did not provide it." in place of "An Origin MAY choose to request signatures from clients that did not initially provide them.", and a paragraph for appendix C, "Signing conditionally", saying that signing only when an origin asks "adds a round trip, and non-idempotent requests may not be safely retried". On 2026-10-08 a participant answered with text under which an origin that refuses unsigned requests "SHOULD include the Accept-Signature field", and "Origins that do not send Accept-Signature in either of these cases SHOULD NOT rely on the presence of signatures in requests unless there is a"
